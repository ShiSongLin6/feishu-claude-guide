# 接入服务卡住时的思考顺序

目标：少走弯路。不要一上来就手工新建应用、补权限、发版本。

## 0. 先翻自己的工具箱，再讲手动步骤
- 用户要对接某个服务时，先搜插件目录和连接器目录，并查看已经连接的账号，再决定怎么做。例如用户要发布到 GitHub：先看是否已连接 GitHub、目录里有没有官方插件，而不是先让用户手动上传。
- 用户提醒“你不是有这个功能吗”，说明漏了这一步：直接去查，不要辩解。
- 先给结论：已经能做 / 装一下就能做 / 确实做不了，各用一句话说清。
- 搜完没有现成的，也要把结果告诉用户（例如知乎：skill、连接器、插件目录都没有，发帖类插件只覆盖海外平台），再动手；动手用浏览器时，先定位控件、输入后核对页面内容，公开发布前把全文给用户确认。

## 1. 先找“已经能用的”
- 问用户是否以前装过、登录过同类工具；用户常常不记得。
- 在已授权的文件夹里找痕迹：配置目录（如 ~/.xxx-cli）、日志、旧脚本。只读文件名、应用 ID、状态码；密钥和令牌一律不读、不显示、不复述。
- 日志里的 HTTP 状态和时间线能说明某个工具是否真的登录成功过。
- 搜索现成方案：官方 CLI 及其配套 skill、插件目录、连接器目录。说明来源（官方/社区）、适用的区域版本（如国内版 vs 国际版），以及是否真的绕开了当前卡点；读过说明但没试过的，要如实说。
- 装第三方 skill 前先扫一遍内容。

## 2. 让报错自己说话
- 点开错误页的“详情/原因”，不要只看标题；能在浏览器里复现就自己复现并读页面文字。
- 区分“表面报错”和“真正拦截的原因”：“权限无法授予”可能只是“账号无法使用该应用”的连带结果。
- 对比“成功的”和“失败的”：应用类型、账号类型、请求的权限、发布状态、可用范围。
- 搜索没有答案就如实说“没找到”，不要编一个结论。

## 3. 受限账号类型要留意
- 个人/平台托管账号下手工创建的企业自建应用，可能在授权、审核、可用范围上受限。官方 CLI 的“一键注册”路径可能绕开这些限制。反复失败时，优先换到官方路径，而不是继续修手工应用。

## 4. 先分清“在哪里执行”
- 云端会话和聊天/协作沙箱是 Linux 虚拟机：碰不到用户 Windows 上安装的 CLI，网络也有白名单。要调用用户本机工具，需要能在本机直接执行命令的本地代码会话，或者运行在本机上的 MCP。
- 装 skill/插件之前，先确认它将在哪种会话里运行、命令在哪台机器上执行，否则装好也调不起来。
- Claude 自己的配置目录是保护区域，助手写不进去，要用户双击脚本完成。不要尝试绕过保护。

## 5. 与用户的分工
- 登录、扫码、点“授权”、发布版本：只能用户来做，提前说清楚。密钥由用户自己粘贴到文件里，不要让密钥出现在对话里。
- 内置浏览器窗格太窄时菜单和抽屉可能点不出来，交给用户手动并给精确步骤；用户也在操作同一窗格时不要抢着导航。
- 把步骤做成可双击的 .bat 放在已授权文件夹里，输出写成文件让助手直接读，用户不用截图。

## 6. 沟通
- 一次只给一个下一步，并说明为什么。
- 发现上一轮判断过于乐观时，直接更正并指出差异。
- 走死路时及时止损：说明哪条路不通、证据是什么，再提出替代方案。
